# Analysis (`packages/analysis`)

## Purpose

Rifter's shared, framework-free analysis library. It turns the player's own match data into an AI coaching report **after** the game ends — deterministic metrics first, then moment detection, then a local LLM (Ollama) that explains curated facts. Desktop, web, and the API all import it; platform adapters (Ollama host management, VRAM probes, file access) live in the apps.

## Pipeline

`Match-V5 (+ timeline) → NormalizedMatch → metrics → moment candidates → prompt → Ollama → validated report`

1. **NormalizedMatch** (`src/normalized-match.ts`) — the canonical input contract every source maps into before any metric runs. The target player is fully modeled (`isTarget`, `targetParticipantId`); the other nine participants carry role/team/champion/stats only — **no puuid, summonerId, names, or any identity field anywhere in the model**. Contents: participants (position, `win`, end-of-game stats subset), per-minute frames (gold/cs/xp/position per participant), normalized timeline events (`champion-kill`, `monster-kill`, `building-kill`, `ward-placed`) tagged `evt-N`, `dataTier`, `gameDurationMs`. Objective events carry `assistingIds` plus explicit team attribution (`killerTeam` on monster kills, `ownerTeam` = building's losing side on building kills); `monsterSubType` distinguishes dragon flavors.
2. **Match-V5 mapper** (`src/match-v5-mapper.ts`) — `matchV5ToNormalized(fixture, targetPuuid)`: consumes only the fields it needs (minimal `MatchV5*` interfaces, incl. `challenges.controlWardsPlaced` — the only place the count exists), marks the target by puuid, converts `gameDuration` s→ms, drops non-essential event types, normalizes non-champion killers (`killerId`/`creatorId` 0 → `undefined`), throws on unknown participant/building `teamId` while a non-100/200 `killerTeamId` (e.g. 300, no credited side) maps `killerTeam` to `undefined`, sorts frames and events ascending (frame order is schema-enforced; metrics rely on it) and tags events with stable ids (positional, per-normalization ephemeral). Output is `normalizedMatchSchema.parse`d — shape violations throw.

3. **Report contract** (`src/report-contract.ts`) — Zod v4 schemas are the single source of truth: `z.infer` gives the TS types, `z.toJSONSchema` gives the schema sent to Ollama's `format` parameter.
   - LLM-facing output: `moments[] {t_start, t_end, label, mistake, fix}` (ms from game start, max 10) + `summary` + optional `topPriority` (index into `moments`). Provenance `metadata {matchId, patch, contractVersion, promptVersion, modelDigest, locale, dataTier}` is **pipeline-owned** — excluded from the LLM schema and attached in code after validation, because the model cannot know its own digest or prompt version.
   - `locale: 'pl' | 'en'` — the LLM writes report prose in the player's UI language; `dataTier` lets the UI always show the tier.
   - `REPORT_CONTRACT_VERSION` is bumped on breaking shape changes; stored reports carry their version (a per-version schema map will be needed when v2 lands).
4. **Validation** (`src/report-validation.ts`) — `validateAnalysisReport(raw, {candidates, gameDurationMs, metadata})` parses the LLM output schema and enforces anchoring with **snap semantics**: a moment is valid only when its `[t_start, t_end]` equals a provided candidate window exactly — the LLM selects candidates and never invents timestamps (interior sub-windows would fabricate precision `basic` data does not have). `t_end` must lie inside the game duration; `topPriority` must index an existing moment. Errors carry a `stage` discriminator: `output` errors are strings suitable for LLM retry feedback; `context` errors are pipeline faults and must never be fed back to the model.
5. **Deterministic metrics** (`src/metrics.ts`) — `computeMetrics(match)` returns the v1 set for the target player: `csPerMin` (last frame CS ÷ frame minute), `killParticipation` (0–1 share of team kills), `visionScore`/`visionPerMin`, `damageShare` (0–1 of team damage to champions), `goldDiffAt15` (target minus same-position enemy gold at the last frame ≤ 15 min), `deaths` + `deathPhases` (early <15 min, mid 15–25, late ≥25), and `objectives` (team-secured monster/building events the target killed or assisted; unattributed `killerTeam` falls back to the killer's side). All metrics are `basic`-tier; anything the input cannot support returns `null` rather than a fabricated number.
6. **Moment detection** (`src/moment-detection.ts`) — `detectMoments(match)` produces `{minTier: 'basic', candidates: MomentCandidate[]}` anchored to timeline events: `death` (every target death, 30 s lead / 10 s tail), `teamfight` (champion-kill clusters, ≤30 s gap, ≥3 kills, first-kill anchor), `objective-lost` (enemy-secured monsters and buildings; the window extends back over kills within 60 s — fight context — else a 30 s fallback lead). Windows clamp to `[0, gameDurationMs]` (collapsing to zero-width for out-of-game events) and sort by `t_start`, tie-broken on `anchorEventId`. Sizes are heuristic constants, not measured precision. Teamfight clustering is temporal-only — positions exist on kill events but are unused, so a cluster may join spatially unrelated kills; prompt wording (#13) should describe these as kill clusters rather than asserting co-presence. Event order (like frame order) is schema-enforced ascending, so clustering and lookback can rely on it.
7. **Prompt building** (`src/prompt-builder.ts`, `prompts/v<N>.md`) — `buildPrompt({match, metrics, candidates, locale, template})` assembles the versioned template plus deterministic fact sections: match context, metrics, each candidate with the events inside its window, and the output-language directive last (recency keeps small models on-locale). `PROMPT_VERSION` selects the active template; callers load `prompts/v<N>.md` themselves (the core is filesystem-free). Participants render as `TARGET`/`team` + position + champion — no identities; monster-kill lines use the canonical `securingTeam` attribution (`no team` when unattributed). Raw `t_start`/`t_end` in ms appear verbatim so the model can echo them for snap validation. Candidates sort by `t_start` and cap at `MAX_PROMPT_CANDIDATES` (40, overflow noted in the prompt) to stay inside the ~8k-token budget; `ward-placed` lines are dropped as noise and `BuiltPrompt.shownCandidates` exposes exactly the rendered set for validation. Golden files under `prompts/golden/` snapshot the builder output per version+locale — a prompt change shows up as a golden diff in review.
8. **Ollama client + pipeline** (`src/ollama-client.ts`, `src/analyze.ts`) — `ollamaGenerateJson(config, {prompt, format})` is a portable-fetch `/api/generate` call: non-streaming, JSON-schema `format`, `keep_alive: 0`, temperature 0, `think: false` (thinking models would burn the output budget on hidden reasoning and emit no answer). Prompt over `maxPromptChars` (~8k-token proxy) throws `budget` before the request. `ollamaModelDigest` reads `/api/tags` for report provenance. `analyzeMatch({match, locale}, deps)` is the facade: metrics → candidates → prompt → LLM → `validateAnalysisReport` with exactly `shownCandidates` — on `output` failure it retries once with the validation errors appended (`maxRetries` config), then throws `AnalysisError` carrying the stage. Result: `{report, usage, retries, timings}` per stage for `analysis_jobs`. `scripts/run-analysis.mjs <fixture> [--locale] [--model] [--record]` runs the whole pipeline against a real local Ollama (imports `dist/`, so `pnpm build` first).
9. Moment candidates have shape `{t_start, t_end, kind, anchorEventId}` with `kind: 'death' | 'teamfight' | 'objective-lost'` — consumed by the prompt builder and later the clip slicer; snap semantics means report moments equal candidate windows exactly.

## Invariants

- The LLM never receives raw dumps or other players' identities; it ranks and explains deterministic candidates.
- Analysis never runs on an in-progress game (Riot compliance).
- Tests are Vitest on recorded/sanitized fixtures — no live LLM, no live Riot API.
